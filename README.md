# Sprix Portal QA Runner

واجهة عربية لاختبار واجهة منصة تعليمية في **بيئة staging مملوكة لك ومصرّح باختبارها**. تدخل كود حساب الاختبار وكلمة مروره من الواجهة، ثم يشغّل Playwright المتصفح، يرسل إجابات اختبار محددة مسبقًا، يتحقق من مؤشرات النجاح/الفشل، ينتظر فتح السؤال التالي، ويعرض تقريرًا مباشرًا مع CSV/JSON.

> هذا مشروع QA وليس محلّلًا عامًا لامتحانات الطلاب. لا يولّد إجابات بالذكاء الاصطناعي ولا ينبغي استخدامه مع حسابات الطلاب الحقيقية أو منصة طرف ثالث دون إذن صريح. يجب أن تكون الإجابات في `test_answers.json` إجابات اختبار معروفة، وأن يكون الهدف بيئة staging. بيانات الدخول لا تُكتب إلى الملفات أو السجلات، ولا تُحفظ cookies أو جلسة المتصفح.

## 1) ارفع المشروع إلى GitHub

1. أنشئ مستودعًا جديدًا مثل `sprix-portal-qa-runner`.
2. ارفع محتويات هذا المجلد كما هي.
3. افتح المستودع ثم **Code → Codespaces → Create codespace**.

## 2) جهّز بيئة Python في Codespaces

من Terminal:

```bash
python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
python -m playwright install chromium
```

إذا طلب النظام مكتبات Chromium إضافية، نفّذ:

```bash
python -m playwright install-deps chromium
```

## 3) اربط بيئة الاختبار

افتح `config.json` وعدّل:

- `base_url`: رابط صفحة تسجيل الدخول في بيئة staging.
- `allowed_hosts`: اسم المضيف نفسه فقط، دون `https://` أو مسار.
- `selectors`: محددات CSS لعناصر تسجيل الدخول والسؤال والاختيارات والإرسال ومؤشر النتيجة وزر التالي.

المحددات الموجودة في الملف أمثلة توضيحية باستخدام `data-testid`، وليست محددات مؤكدة لموقعك. الأفضل إضافة `data-testid` ثابتة في كود المنصة لتكون اختبارات الواجهة مستقرة. لا تستخدم رابط الإنتاج أو حساب طالب حقيقي.

**قيد حماية:** التطبيق يرفض التشغيل إن لم يكن الرابط HTTPS، أو المضيف غير موجود حرفيًا في `allowed_hosts`، أو `mode` ليس `authorized_staging_qa`.

## 4) ضع إجابات الاختبار المتوقعة

عدّل `test_answers.json`. لكل سؤال:

- `chapter`: اسم الشابتر للتقرير.
- `question_contains`: عبارة مميزة من نص السؤال. إن لم تطابق الصفحة، لن يرسل الاختبار إجابة لذلك السؤال.
- `answer_text`: النص المطابق تمامًا لخيار الإجابة التجريبي الظاهر على الصفحة.

مثال:

```json
{
  "questions": [
    {
      "chapter": "Chapter 1",
      "question_contains": "What does HTTPS provide",
      "answer_text": "Encrypted communication"
    }
  ]
}
```

لا تترك قيم `REPLACE WITH ...` الافتراضية؛ سيعتبرها المشروع نصوصًا تجريبية ولن يجدها في المنصة. ترتيب الأسئلة في الملف هو ترتيب تنفيذها. استخدم حساب اختبار وبيانات يمكن إعادة ضبطها.

## 5) شغّل الموقع

```bash
python app.py
```

في Codespaces سيظهر إشعار المنفذ `8000`، اختر **Open in Browser**. على استضافة أخرى، اضبط متغير `PORT` حسب متطلبات المنصة.

## 6) شغّل اختبارًا

1. أدخل كود حساب الاختبار وكلمة مروره في لوحة الموقع.
2. اضغط **ابدأ الاختبار**.
3. تابع حالة كل سؤال من سجل الأحداث.
4. عند انتهاء التشغيل، حمّل CSV من الرابط الموجود في اللوحة. يوجد أيضًا `output/report.json` داخل بيئة التشغيل.
5. إذا توقف، راجع سجل الأحداث والمحددات في `config.json`.

## التقرير

النتائج المحتملة: `passed` (ظهرت علامة النجاح)، `failed` (ظهرت علامة الخطأ)، `needs_review` (النتيجة غير واضحة أو الانتقال لم يكتمل). الانتقال للسؤال التالي وحده لا يثبت صحة الإجابة؛ يجب ضبط مؤشري `correct_indicator` و`incorrect_indicator` بما يطابقان واجهة staging.

## ملاحظات مهمة

- لا ترسل كلمات المرور أو رموز الجلسات في Issues أو سجلات GitHub.
- لا تضع بيانات دخول داخل ملفات المشروع أو GitHub Secrets إذا كان يمكن إدخالها وقت التشغيل.
- إذا كانت المنصة SPA، اضبط `post_login_ready` على عنصر يظهر بعد اكتمال تسجيل الدخول.
- إذا كان السؤال يحتوي على خيارات مخصصة غير `input`، اضبط `option` على العناصر القابلة للنقر التي تمثل الخيار كاملًا.
- إذا كانت المنصة تفتح السؤال التالي تلقائيًا بعد الإرسال، اجعل `next` فارغًا في `config.json`، وعدّل منطق انتظار الانتقال حسب واجهة المنصة؛ الإعداد الحالي يتوقع زر التالي عندما تكون هناك أسئلة لاحقة.
- الاختبار الحقيقي لن يعمل قبل تعديل `config.json` و`test_answers.json` ليتطابقا مع HTML الفعلي لبيئة الاختبار. المشروع لا يستطيع معرفة محددات موقعك من دون فحص الصفحة أو إضافة `data-testid`.
